# Native Crates

Contributor-facing map of the Rust crates under `crates/`. These crates back
`@veyyon/natives` and the embedded shell/PTY runtime. They are intentionally
internal: end users see `@veyyon/natives` exports, not these crate APIs.

For the consumer-side runtime contract see
[`natives-architecture.md`](./natives-architecture.md). For inclusion policy
covering when a crate should be promoted to user-facing docs, see
[`user-facing-packages.md`](./user-facing-packages.md).

## Crate map

| Crate | Path | Role |
| --- | --- | --- |
| `veyyon-natives` | [`crates/veyyon-natives`](../../crates/veyyon-natives) | Top-level N-API `cdylib`; aggregates the other crates and exposes the JS-visible API. Turning a Rust error into the message a JavaScript caller reads has one owner, `napi_error`: `to_napi(err)` passes the error's own `Display` through unchanged, and `to_napi_with(context, err)` writes `context: reason`, which is the convention every module used to spell out by hand. A message that is composed rather than wrapped stays where it is made, since there is no shape for a helper to own, and `iofs::map_walker_error` stays a specialist because the walker's two failure kinds take different shapes. Every error from the owner is `Status::GenericFailure`; the one place that names a status explicitly is the panic-unwind path in `task.rs`. `tests/napi_errors_have_one_owner.rs` scans the crate so a second copy of either shape fails the build rather than passing review. |
| `veyyon-shell` | [`crates/veyyon-shell`](../../crates/veyyon-shell) | Embedded shell / PTY / process management split out of `veyyon-natives` (wraps `brush-*`). The output minimizer's `primitives::strip_ansi` is one of two implementations of ONE contract: this one runs inside the minimizer, and `stripAnsi` in [`packages/utils/src/strip-ansi.ts`](../../packages/utils/src/strip-ansi.ts) runs in the TUI and in a browser bundle that cannot import a Rust crate. Neither is free to invent its own rule, so the cases live outside both languages in [`fixtures/ansi-strip-corpus.json`](../../fixtures/ansi-strip-corpus.json) and both suites read them for exact bytes and for idempotence (`crates/veyyon-shell/tests/ansi_strip_contract.rs`, `packages/utils/test/strip-ansi.test.ts`). The contract: remove every well-formed CSI (`ESC [`, parameter bytes `0x30-0x3f`, intermediate bytes `0x20-0x2f`, one final byte `0x40-0x7e`) and every well-formed OSC (`ESC ]`, a body holding neither BEL nor ESC, terminated by BEL or by ST); an escape that opens neither is dropped alone and the text after it is kept, which is both what a capture cut mid-escape needs and what makes a pass a fixed point. Add a case to the corpus, never to one language. |
| `veyyon-ast` | [`crates/veyyon-ast`](../../crates/veyyon-ast) | tree-sitter-based code summarizer and AST utilities; 50+ language grammars. |
| `veyyon-iso` | [`crates/veyyon-iso`](../../crates/veyyon-iso) | Task isolation backend resolver: APFS clones, btrfs/zfs reflinks, overlayfs, projfs, rcopy. Plain-mode change capture emits patch text through `veyyon-diff-kernel`, so it cannot disagree with the `diff` builtin about what a line is or what counts as binary; it assembles the `diff --git` header itself. |
| `veyyon-glob` | [`crates/veyyon-glob`](../../crates/veyyon-glob) | Glob pattern normalization and matching, with fast paths for the common extension and basename shapes; shared by the glob, grep, and ast-grep tools. It also owns `walk_depth_bound`, the deepest path a normalized pattern can match, which is sound only because walk-relative globs compile with `literal_separator(true)`. A walking tool does not call either function itself: `veyyon_walker::CompiledWalkGlob::compile` applies the normalization and reports the bound through `depth_bound()`, so the pattern and the depth it implies cannot be taken apart. They used to be, and only one of the three tools took both: the glob tool bounded its walk while grep and ast-grep passed `usize::MAX`, so `--glob 'src/*.ts'` traversed the whole tree and filtered everything below depth two back out, with correct results and a full traversal's cost. |
| `veyyon-keys` | [`crates/veyyon-keys`](../../crates/veyyon-keys) | Terminal key sequence parsing: the Kitty keyboard protocol, the legacy escape sequences, and the normalized key ids both map to. |
| `veyyon-text` | [`crates/veyyon-text`](../../crates/veyyon-text) | ANSI-aware measurement and slicing over UTF-16: visible width, wrapping, truncation, column slicing, and overlay segment extraction. |
| `veyyon-walker` | [`crates/veyyon-walker`](../../crates/veyyon-walker) | Parallel filesystem walker (ignore + globset) shared by grep, glob, and fs-scan cache. One function answers "is this entry walked at all": `FastIgnore::admits`, which applies the hidden rule, the `.git` and `node_modules` pruning rules and the ignore files, and both traversals ask it so they cannot drift apart. Two options shape the ignore rules. `require_git` restricts the git-specific sources, `.gitignore`, `.git/info/exclude` and the global gitignore, to directories inside a repository, the way git itself reads them; it is off by default and the `rg` and `fd` builtins turn it on because that is what those tools promise. `.ignore` is not a git file and applies either way. `WalkOverrides` carries caller-named globs, `rg --glob`/`--iglob` and `fd --glob`, which OUTRANK the hidden rule and the ignore files: a file matching one is walked even when it is ignored or hidden, and once any include glob exists a file matching none is dropped. Directories differ on purpose, and the difference is what makes the rule usable: a directory opens up only when a glob names the directory itself, so `--glob '*.txt'` does not descend into an ignored directory while `--glob '*'` does. Setting overrides disables the scan cache for that request, because a cache entry is keyed by `WalkOptions` and those cannot describe a glob set. `CompiledWalkGlob` is the other glob surface, the one a tool hands to `WalkFilter::glob`, and it is where a raw pattern becomes a filter: `compile(pattern, recursive)` normalizes through `veyyon-glob` and `depth_bound()` reports how deep the result can match, which is the value the request's `depth` takes. The two live together so a caller cannot bound a walk with a depth measured from a different pattern than the one it compiled. |
| `veyyon-uu-grep` | [`crates/veyyon-uu-grep`](../../crates/veyyon-uu-grep) | Both search builtins on `grep-regex` / `grep-searcher`, run in-process: `grep` (entry `veyyon_uu_grep::run`) and `rg` (entry `veyyon_uu_grep::run_rg`). They keep separate flag vocabularies on purpose, since GNU grep and ripgrep genuinely disagree, and share what must not drift: the matcher and searcher through `veyyon-grep-kernel`, and how a directory walk ends through the crate's `walk_end` module. In `rg`, a flag and its `--no-` partner are resolved by clap through `overrides_with`, so the one written LAST on the command line wins, which is what ripgrep does; the same holds for the three-way `-i` / `-s` / `-S` group. Do not re-derive one of these with a conjunction such as `cli.trim && !cli.no_trim`, because that picks a winner by side and gets one of the two orders wrong. `--stats` and `--heading` print real output, and `-p` is wired to the heading and line-number halves of what it aliases; the color half it also implies is not emitted, because the builtin writes into a captured buffer rather than a terminal. When a flag cannot be implemented, say so in its help text rather than declaring the field with a leading underscore and letting it parse into nothing. `walk_end` owns the cancellation heartbeat every walk passes to `veyyon-walker` and the rule that a cancelled walk sets the error status while printing nothing, because the shell wrapper reports cancellation itself. A walk failure reads `<tool>: <path>: <message>`, the same shape as every other diagnostic in both tools, rather than the walker's own `Display`. The `grep` half owns one thing the `rg` half has no use for: `bre`, which translates a POSIX BASIC regular expression into the syntax the two engines share, because `-G` asks for a syntax where `+ ? | ( ) { }` match themselves and `\+ \? \| \( \) \{ \}` are the operators. Every rule in it was measured against GNU grep 3.11, its errors carry GNU's wording, and a pattern using a back-reference is routed to PCRE2 because the Rust engine cannot compile one. With NO syntax flag the builtin reads a MODERN regular expression rather than a basic one, which is a deliberate difference from GNU and is pinned by a test so it cannot drift back into an accident. Two rules in the `grep` half have one owner each, both found by its GNU differential suite. `GrepSink::begin_search` prints the group separator between one input's records and the next's, which GNU does wherever it separates two gaps inside a file, `-C0` included, so the run needs state that outlives one input: that is `RunState`, which carries `printed` beside `had_error` and replaced the `&mut bool` that used to be threaded on its own. A DIRECTORY operand read as a file is an input that was searched and matched nothing, not an operand that failed to open, so `-c` prints a zero count for it and `-L` lists it; the arm searches an empty reader to say that, which keeps one printer for every count line. `io_reason` decides how an operating-system failure is worded: GNU prints the reason alone, so the ` (os error N)` suffix `io::Error` appends is stripped for every diagnostic in this half. The `rg` half deliberately keeps that suffix, because ripgrep prints it, which is why the rule has one owner per tool. The pattern-syntax flags are also the one place a conflict is refused instead of resolved by taking the last flag: two different kinds exit 2 with `conflicting matchers specified`, as GNU does, since that choice decides what a pattern means. WHICH SPAN a match reports has one owner too, `PosixLongest`, and it exists because GNU grep is a POSIX matcher: where several alternatives match at the same position it reports the LONGEST, so `grep -o -E 'hit|hit hit'` over `hit hit hit` prints `hit hit` and then `hit`. Both engines this builtin can use are leftmost-FIRST, the Rust engine and PCRE2 alike, and each would print `hit` three times. The rule is a SECOND automaton over the patterns the first engine actually compiled, built with regex-automata's `MatchKind::All` so an anchored overlapping search from a known start reports every end a match could have there; the longest is GNU's answer. It is built by `build_matcher` beside the matcher itself, because that is where both halves it needs live, and only for a run that prints a span, so no other mode pays for it: the first engine still decides whether a line matches and where a match starts, and the second is asked only from `print_only_matching`. Under `-w` the ends are filtered, since the start already satisfies the word rule and only the end can break it. Two runs keep the leftmost-first span deliberately and both are recorded rather than silent: `-x` has no span to choose, and a pattern that needs PCRE2 has no equivalent automaton here because the construct is not regular. The `grep` differential corpus carries sixteen cases for this rule, including both branch orders, a bounded repeat, `-w`, `-i`, `-x`, `-F`, a back-reference, and `-c` proving the counting mode is untouched. In `rg`, three questions each have exactly one owner, and each of the three used to be answered in several places at once. `resolve_sort` decides whether and how a search orders its files: any key at all routes to the collected search, the time keys stat each file once rather than inside the comparator, and the key is validated in `run` so no later path can be handed a value it would have to ignore. `display_path` decides what a path prints as: the operand VERBATIM in front of the walked remainder, or nothing in front for the implicit root, which is why `rg hit .` says `./a.rs` and `rg hit` says `a.rs`. The ignore sources are `veyyon-walker`'s, one option per source, so `--no-ignore-dot` and `--no-ignore-vcs` turn off different files and `--no-ignore` is the master switch over all of them; the caller's `--glob`/`--iglob` become one `WalkOverrides` that BOTH the walk and `PathFilters` consult, so a whitelisted file cannot be admitted by one and dropped by the other. Where a file's bytes come from has one owner too, `open_file_input`: the file itself, the standard output of the `--pre` program, or a decompressor under `-z`, in that order, since `--pre` overrides `-z` while a file its `--pre-glob` set leaves out still reaches `-z`. Every child process starts through `spawn_reader`, which looks the program up on the SHELL's `PATH` through `veyyon_uutils_ctx::resolve_program` and runs it in the shell's working directory with the shell's exported environment, because the host process environment belongs to the host and not to the command. A decompressor that cannot start is REPORTED and the run exits 2, which diverges from ripgrep on purpose: `grep_cli` logs that failure at debug level and reads the file as-is, so ripgrep on a machine without `brotli` searches raw compressed bytes and calls the result "no match". A diagnostic names the file the way the caller wrote it, never the absolute path the builtin resolved internally, which is why `process_file` takes the reported name separately from the prefix its records carry. Three more questions have one owner each, and all three were found by the ripgrep differential suite. Binary detection is chosen by how the file was REACHED, `quit` for the walk and `convert` for an operand, and never by which mode is printing; what a summary mode does differently is decline to report a file the quit detection fired on, which is `RgSink::filtered_as_binary` and covers `--include-zero`'s zero line and `--files-without-match` too, because a count taken from the bytes before a NUL is smaller than the file's real count and reads as content. `RgSink::search_separator` owns the mark between one file's output and the next's: empty under `--heading`, so the blank line between groups is that separator rather than a second rule, the context separator when context was requested, and nothing otherwise. `print_multi_line_records` owns the shape of a `--multiline` match, which is reported line by line so every line carries a prefix; the line number counts up, the byte offset is each line's own, and the column is the match's, repeated, which is ripgrep's behaviour and is reproduced rather than corrected. The matcher's line terminator is set in ONE place for the same reason: `--crlf` leaves `MatcherFlags::line_terminator` empty because `RegexMatcherBuilder::crlf` already set a two-byte terminator that no `Option<u8>` can name, and overwriting it made grep-searcher refuse every file. How a bad command line is worded has one owner as well, `argv_diagnostic`, and it exists because ripgrep parses its own flags while this builtin parses with clap. ripgrep prints one line and no usage block: `rg: error parsing flag <flag>: <reason>` for a value it cannot read, `rg: missing value for flag <flag>: ...` for a flag whose value was left off, and `rg: unrecognized flag <flag>` for a flag it does not know. `argv_diagnostic` translates clap's three matching error kinds into those three shapes and returns `None` for help and version, which are not failures and keep clap's own rendering. It reports the spelling the command line used rather than the one clap declares, through `typed_spelling`: ripgrep echoes `-m` for `rg -m abc`, the last spelling on the line wins because that is the value that was parsed, and a short cluster names the flag it holds, so `-imabc` names `-m`. Each reason has one owner too: `parse_flag_number` for every numeric flag, `parse_size` for the two ways a size can be refused, `parse_regex_engine` because `--engine` names the engine rather than listing the choices, `parse_color_choice` because a value ripgrep refuses must not be accepted here, and `unrecognized_choice` for the phrase `--color` and `--sort` share while being checked at different times. A size is digits with an optional UPPERCASE `K`, `M` or `G`, so `1k` is a mistake: accepting it would quietly change which files a filter searches. Every value-taking flag carries `allow_hyphen_values`, because in ripgrep a flag always takes the next argument, so `rg -m -3` refuses `-3` as a number instead of calling it an unknown flag; the positional operand list deliberately does not, so an unknown flag is still an unknown flag. `add_type_definitions` is the one place a `--type-add` definition is parsed, and `build_path_filters` calls it even when no `-t`/`-T` selects a type, since a malformed definition is a mistake in the command line whether or not the run reads it; it runs there on a builder without the default definitions, so a run that filters nothing does not pay for loading them. Every `Result<_, String>` producer in the file returns its message WITHOUT the `rg: ` prefix and every printer adds it once, which is the rule that stops `rg --type-list --type-add nocolon` printing `rg: rg: `. WHICH OUTPUT a run produces has one owner as well, `OUTPUT_MODE_FLAGS`, and it is a clap `overrides_with_all` group rather than code: `--json`, `-c`, `--count-matches`, `-l`, `--files-without-match`, `--files` and `--type-list` are seven answers to one question, so the flag written LAST wins and clap drops the rest. Inside a cluster the rightmost letter wins, since clap resolves a cluster left to right, so `-cl` lists and `-lc` counts. `-q`, `-o` and `--vimgrep` are deliberately outside the group: `-q` asks for the exit code and still gets a `--json` summary record, while `-o` and `--vimgrep` choose how a matching line is written and are ignored outright in JSON mode. `--no-json` is outside it too, because its rule is narrower than an override: it returns the mode to the standard one only when the mode is CURRENTLY JSON, so `rg -c --json --no-json` prints lines while `rg --json -c --no-json` prints a count, and `json_is_cancelled` expresses that as one comparison of the two flags' argv positions. That is why `run` parses through `ArgMatches` instead of `try_parse_from`: the position is the only thing the derived struct does not carry. `--json` combined with any of the others used to be REFUSED here with a diagnostic ripgrep does not have, and the other six resolved by a fixed precedence, so `-c -l` and `-l -c` gave the same answer where ripgrep gives two. `reports_whole_search_numbers` owns the question both early-exit predicates ask, because `--json` is the second way to ask for numbers about the whole search and both used to ask it as `!stats` alone: `rg --json -q` reports every match in its summary record, so the search cannot stop at the first one. In JSON mode `-q` is routed through the ordinary sink rather than the JSON printer, which is what makes the record read `bytes_printed: 0` while still counting everything. `write_json_summary` owns the one record `grep-printer` does not write, and it reproduces two things that read like ripgrep's slips because a consumer diffs the bytes: it carries `elapsed_total` beside `stats.elapsed`, the same pair `--stats` prints as "seconds spent searching" and "seconds total"; and its keys are SORTED, `data` before `type` and `human` before `nanos` before `secs`, where the `begin`/`match`/`end` records print `type` first and their fields in declaration order, because ripgrep serializes this one record through a map. `json_duration` is the one owner of the three-field duration shape, and `human` is six-decimal seconds (`0.000014s`) rather than Rust's `Debug` for a `Duration`. Both writers list their fields in ALPHABETICAL order, which is the one order that is right however `serde_json` is built: the workspace turns `preserve_order` on, so the map keeps insertion order, and without that feature the map sorts. Writing them in reading order instead made the record's bytes depend on which crates were in the build, since a single-crate build sorted them and a workspace build did not. `--generate` writes a man page or one of four completion scripts, and it generates them from `uu_app()`, the SAME clap command the parser uses: a completion listing a flag this builtin refuses, or omitting one it accepts, is a lie the shell repeats at every tab press. That makes the artifacts a deliberate divergence from ripgrep's own, which describe ripgrep's larger flag table, so the tests assert the contract instead of the bytes: every VISIBLE long flag appears in all five artifacts, in each artifact's own dialect (fish writes `-l json`, roff writes `\-\-json`), while the seven hidden negations are absent from the man page, offered by all four completions, and still parsed. Both halves of that split are ripgrep's measured behaviour. `--generate` is a member of `OUTPUT_MODE_FLAGS`, so `rg -c --generate man` writes the page and `rg --generate man -c` runs a count; it short circuits before the operands are resolved, because it reads none of them. HOW output is buffered is one state with one owner too, `Buffering`, and it answers the question ripgrep's own help states from both sides: `--line-buffered`, `--no-line-buffered`, `--block-buffered` and `--no-block-buffered` are four spellings of one choice, each overriding all of them, so the last one on the command line wins and a `--no-` spelling returns the decision to the destination rather than forcing the other mode. The destination is the DEFAULT and not a fallback: a terminal gets line buffering so a long search shows results while it runs, a pipe or a file gets block buffering because it is faster, and the builtin learns which through `veyyon_uutils_ctx::stdout_is_terminal()` since only the host can know. Line buffering is a `LineWriter`, not a write straight through: a matching line is emitted as five fragments (path, separator, line number, separator, line), so an unbuffered sink cost five write syscalls per match on exactly the runs that asked for streaming. |
| `veyyon-diff-kernel` | [`crates/veyyon-diff-kernel`](../../crates/veyyon-diff-kernel) | One owner for turning two texts into unified-diff text: what counts as a line, what a line's comparison KEY is under the GNU ignore flags, how the hunks are formatted, and how far into a file a NUL still means binary. Shared by the `diff` shell builtin and by plain-mode change capture in `veyyon-iso`, which each used to hold their own copy. The copies had already drifted in both directions that matter: they split lines differently, so a file containing a lone `\r` was one line to one and two to the other, and they disagreed about the NUL window, so a file with a NUL 5 KiB in got a patch from one and a refusal from the other. A plain library crate rather than code inside a consumer, for the same reason `veyyon-grep-kernel` is one. Structural tests in the crate fail if a second owner of the splitter, the sniff, the window, or the `similar` line differ appears, and a paired test fails if either consumer stops importing it. It also owns WHERE a change group sits when several placements cost the same, which is a question the aligner cannot answer on its own: `similar`'s Myers and GNU's pick different equal-cost alignments, and the choice is user visible because it decides which lines a hunk calls changed and therefore what `-B` then filters. Two things settle it. The search order itself prefers the deletion, so a swapped pair reads `-a`, ` b`, `+a` as GNU writes it, which is a property of GNU's own search rather than something imposed afterwards. Then `shift_one_side`, which is GNU's `shift_boundaries`, slides every run of changed lines to a canonical place: back while the unchanged line before it equals its last changed line, which merges runs, then forward while its first changed line equals the line after, and finally back to the last point where it faces a changed run on the other side. Forward runs second so an unmerged run ends as far forward as it can, which is what makes the result independent of where the run started. The alignment itself is GNU's too. `compareseq` and `diag` are ports of the bidirectional Myers search from GNU's `analyze.c`, run with the heuristics off, which is what `diff --minimal` does. That was the only way to reach the last of the divergences: where several alignments cost the same, the answer is decided by which diagonal the search examines first, and two equal-cost alignments can pair the unchanged lines with DIFFERENT lines, so no rule applied to the flags afterwards turns one pairing into the other. GNU recurses; this keeps an explicit stack, so a file whose edit script is as long as the file cannot exhaust the process stack. The equivalence classes are numbered from ONE map across both sides, because every comparison in the search is a class from one side against a class from the other. Measured against GNU diff 3.10 over the 784 pair-and-flag cases in `tests/gnu_unified_differential.rs`, and it agrees on ALL of them with no exception recorded: over the original 464, `similar`'s Myers alone disagreed on 72, computing the alignment on the swapped input and mirroring each op back took it to 33, the boundary shifting to 16, a `pull_unchanged_lines_back` normalization to 8, and `compareseq` closed the last 8 at once. Both of those crutches are gone with `compareseq` in place. The mirror existed to bend a foreign tie preference toward GNU's and GNU's own search does not need bending. The pull was re-measured on the widened corpus and turned out to cost more than it bought, 29 disagreements against 10, and it was an invented approximation of a pass GNU actually has: `discard_unmatched` is GNU's `discard_confusing_lines`, which removes every line whose class does not occur in the other file at all, marks it changed, and compares the REDUCED sequences. That is not an optimization. A line with no counterpart cannot be in any common subsequence, so removing it cannot change the cost, but it changes which lines the search sees as adjacent and therefore which of two identical lines stays unchanged, which is what those 10 cases were about. Only the exact half is ported; GNU's second half discards lines that DO occur but occur often enough to look like noise, which changes the cost and needs a file past GNU's `many_lines` threshold. Grouping the surviving changes into hunks is this crate's own `group_ops` rather than `similar::group_diff_ops`, because GNU's join distance is not a constant: two changes share a hunk while fewer than `2 * context + 1` unchanged lines separate them, and only `context` when the change about to be reached is IGNORABLE, which under `-B` means a change whose every line is blank. The asymmetry is measured over both orders at two context sizes and it is one-sided, reading the ignorability of the change ahead and nothing else. A hunk then survives when some change in it is not ignorable, which is how `-B` reports nothing at all for a pair that differs only in blank lines. A case that starts agreeing must lose its `divergence` note in the same change, which the suite enforces by failing on a stale exception. |
| `veyyon-uu-diff` | [`crates/veyyon-uu-diff`](../../crates/veyyon-uu-diff) | `diff` as an in-process shell builtin on `veyyon-diff-kernel`, which owns the alignment and the unified output: unified output, `-q`, `-N`, `-s`, `-a`, `--label`, the comparison flags `-i`, `-w`, `-b`, `-Z`, `-E` and `-B`, and directory comparison where `-r` controls descent (without it a shared subdirectory is reported as `Common subdirectories:` and does not affect the exit code). The comparison flags decide equality without changing what is printed, so a line matched under `-w` is printed with its own trailing whitespace intact. `similar` has no comparator hook, which is why the unified formatter is hand-written in `veyyon-diff-kernel` rather than borrowed from it; that crate owns the key transform, the line splitting, the hunk formatting and the binary sniff, and the format is pinned byte for byte against the `similar` formatter it replaced. Two rules there were measured against GNU diffutils 3.10 rather than assumed: a line ends at a `\n` and nowhere else, so a lone `\r` does not start one, and `-B` drops a whole hunk in which every change is blank rather than filtering blank lines out of a hunk it keeps, with the hunk boundaries themselves moving because a blank-only change joins its neighbour over a shorter distance than a real one. Entry: `veyyon_uu_diff::run`. |
| `veyyon-uutils-ctx` | [`crates/veyyon-uutils-ctx`](../../crates/veyyon-uutils-ctx) | Thread-local stdio + cwd context shim for embedding vendored uutils as in-process shell builtins. It also owns program LOOKUP: `resolve_program` resolves a program name against the scope's `PATH` (entries in order, an empty entry meaning the working directory, a name holding a separator resolved against the scope's directory), because `Command::new` searches the environment the HOST process was started with, and a builtin's `PATH` is the shell's exported one. Every builtin that spawns a child resolves through it first, then runs the child with `current_dir(cwd())` and `env_clear().envs(env_snapshot())`. It also carries one thing about stdout that this side cannot derive: `ScopeIo::stdout_is_terminal`, read back through `stdout_is_terminal()`. A utility sees stdout as a `Box<dyn Write>` with no descriptor behind it, and the process-global `std::io::stdout()` answers for the SHELL's stdout, which is the wrong answer for a redirected command and for every stage of a pipeline, so the HOST declares it per command: `veyyon-shell` asks the command's own `OpenFile` (a `Stdout`, `Stderr` or `File` handle answers `is_terminal()`; a pipe or a custom stream is never a terminal), and a test or a capture buffer passes `false`, which is the truth about a `Vec<u8>`. With no scope installed the answer is `false` rather than the host process's tty. `rg` reads it to choose line over block buffering. |
| `veyyon-test-scratch` | [`crates/veyyon-test-scratch`](../../crates/veyyon-test-scratch) | Scratch directories for this workspace's Rust tests. Dev-dependency only, nothing ships it. `scratch_dir(label)` returns a `TempTree` whose `Drop` removes the directory, so cleanup happens on the failing path too, which a `remove_dir_all` at the end of a test does not. It exists because twenty-odd test modules across six crates built a path under `env::temp_dir()` and never removed it, and eight more had each written their own copy of the same guard. See [Test scratch directories](#test-scratch-directories). |

## Test scratch directories

A Rust test that needs a directory on disk asks `veyyon-test-scratch` for one:

```rust
use veyyon_test_scratch::scratch_dir;

let tree = scratch_dir("my-crate-some-case");
std::fs::write(tree.join("a.txt"), "hit\n").expect("fixture");
// `tree` removes itself here, including if the test panicked on the way.
```

`TempTree` derefs to `Path` and implements `AsRef<Path>`, so `tree.join(..)`,
`tree.display()`, `&tree` where a `&Path` is wanted, and the generic
`impl AsRef<Path>` parameters most standard library functions take all work as they
did when the value was a `PathBuf`. Add the crate as a dev-dependency:

```toml
[dev-dependencies]
veyyon-test-scratch = { path = "../veyyon-test-scratch" }
```

Do not build the path yourself, and do not write your own guard. Both were the norm
here and both went wrong. Twenty-odd test modules joined a unique name onto
`std::env::temp_dir()`, created it, and never removed it: in `veyyon-uu-grep` alone
that pattern sat at 80 call sites, so one `cargo test` left about ninety directories
in the system temp directory permanently, and on the machine where this was found
`/tmp` had reached tens of thousands of stranded directories and the root filesystem
filled up. Eight other modules did write a guard, each its own copy of the same
twenty lines.

Two things make this specific to Rust. The JavaScript suites are covered by a bun
preload that wraps `mkdtemp` and `mkdir` and collects whatever a test process made
(`packages/utils/test/helpers/temp-dir-janitor.ts`); no preload, and no
after-every-test hook, reaches a Rust test binary. And CI never feels it, because the
container is discarded after the run, so the cost lands only on a developer's disk
where no gate is looking.

`crates/veyyon-uu-grep/tests/test_scratch_is_always_owned.rs` scans every `.rs` file
under `crates/` and fails when test code names a path under the system temp directory
outside `veyyon-test-scratch`. Production use is not flagged: a cache or a spill path
belongs to a running program and its lifetime is that program's problem, so the scan
reads an integration test in full and a `src` file only from its first `#[cfg(test)]`.

One case the guard cannot serve is a directory shared by every test in a file through
a `static`. A `static` never drops, so nothing would remove it. Build the tree per
test instead, as `crates/veyyon-walker/tests/perf.rs` does; if the cost is real,
measure it before reaching for a shared one.

## Policy

These crates are implementation details. End-user docs live with the consuming
package (`@veyyon/natives`) and the architecture pages above. Promote a
crate to a dedicated user-facing doc only when it grows a standalone CLI or
public API consumed outside `packages/natives`.
